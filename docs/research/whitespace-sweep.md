# Whitespace sweep: prior art landscape and verdict on §1.2

Access date for all sources: 2026-07-16. Evidence base: the fourteen adversarial note files in `docs/research/notes/` (Task 0.1), each of which records primary source citations with access dates and the strongest refutation sentence its subject offers. This document synthesizes those notes into the landscape table, the verdict on the novelty claim, and reusable positioning language. It is the go or no go input for the M0 gate.

Claim under test, quoted verbatim from `requirements.md` §1.2:

> smithmark is the first attestation framework that treats **capability declarations as signed, policy-consumable artifacts** for MCP servers and skills — composing npm provenance, Sigstore, SLSA, and CycloneDX rather than replacing them, and closing the loop from publication (maker's mark) to admission (assayward policy).

## Summary for the gate

The claim as written fails on the word "first": signed capability declarations consumed by policy already exist for skills (Enclawed) and, in narrower form, for MCP servers (studiomeyer-io/mcp-server-attestation) and MCP tool definitions (ETDI). The claim survives with narrowing to the composition: no prior work that signs a capability declaration covers both artifact kinds, none composes npm provenance, Sigstore, SLSA, and CycloneDX through a portable attestation format, and none separates the maker's mark from the policy gate that consumes it. Recommendation: GO, conditional on adopting the replacement §1.2 sentence in the verdict section below.

## 2. Verdict on §1.2

### (a) Does any prior art treat capability declarations as signed, policy consumable artifacts for MCP servers or skills?

Yes. Three items, each covering a slice of the claim, and each predating smithmark:

**Enclawed (arXiv 2605.00424, dated 2026-05-15, implemented at github.com/metereconsulting/enclawed).** For the skills half, the core idea is occupied. Skills carry Ed25519 signed manifests declaring capabilities from a fixed vocabulary (`net.egress`, `fs.read`, `fs.write.rev`, `fs.write.irrev`, `tool.invoke`, `spawn.proc`, `publish`, `pay`, `mutate.schema`) that is close to smithmark's own declared set, and a policy gate consumes the declaration: "A skill's manifest must enumerate every capability its content intends to invoke. A capability not in M.caps is denied at the gate, regardless of what the skill content asks." This is a signed capability declaration for a skill, consumed by policy, shipping as open source. Its limits, from its own paper: it rolls its own Ed25519 trust root and Bell LaPadula style classification rather than composing npm provenance, Sigstore, SLSA, or CycloneDX; it covers skills only, not MCP servers; and its policy gate is the enclawed runtime itself, verified at bootstrap, not a portable attestation consumed by an independent policy engine across a publish to admission pipeline (`notes/enclawed-skills-verifiable-artifacts.md`).

**studiomeyer-io/mcp-server-attestation.** For the MCP server half, a narrower version exists: an Ed25519 signed tool manifest providing "cryptographic verification of which tools a server is allowed to expose and which spawn calls it is allowed to make," with a runtime gate that validates spawn calls against the signed allowlist. Its limits, from its own README: network egress control, sandboxing, and OAuth hardening are explicitly out of scope, so the manifest is a tool and spawn allowlist rather than a capability manifest over egress, filesystem, exec, env, and secrets; trust is TOFU (each user pins the developer's own key at first use, with no registry to admission loop); Sigstore Rekor is an optional cross reference rather than an integrated composition; no skills; and maturity is minimal (v0.1.1, 0 stars, 26 commits at access time). Maturity does not rescue the §1.2 wording, however: the project exists and is published (`notes/studiomeyer-mcp-server-attestation.md`).

**ETDI (arXiv 2506.01333, submitted 2025-06-02).** The nearest paper level neighbor, and the one the requirements document itself flagged. ETDI binds MCP tool definitions to signed JWTs, makes versions immutable, and proposes a policy engine that evaluates declared permissions: "A tool's required capabilities (e.g., OAuth scopes) are declared in its signed definition." Its limits, from its own paper and repositories: capability means OAuth scope, not the resource surface (egress, filesystem, exec, env, secrets) smithmark declares; verification happens client side at tool discovery, not as a published artifact gated at admission; there is no composition of npm provenance, Sigstore, SLSA, or CycloneDX (the paper cites Sigstore literature without integrating it); no skills coverage; and the reference implementation survives only as a fork, with upstream PR #845 to modelcontextprotocol/python-sdk closed unmerged on 2025-07-18 and redirected to a specification first process (`notes/etdi.md`).

Everything else in the table either does not sign (mcp-scan, MCP Registry, SkillGuard, agent-manifest, CycloneDX issue #895), signs something other than a capability declaration (npm provenance, ToolHive, Docker MCP Catalog, NVIDIA, the TEE server, the runtime manifest paper), or both.

### (b) Does the claim survive as written, survive with narrowing, or fail?

**As written, the claim fails.** A blanket "first attestation framework that treats capability declarations as signed, policy-consumable artifacts for MCP servers and skills" will not survive contact with Enclawed alone, which is implemented, dated before smithmark, and matches the sentence's core for skills nearly word for word. studiomeyer-io/mcp-server-attestation and ETDI falsify looser readings from the MCP side. The abstract idea at the center of the sentence, a signed capability declaration consumed by policy for an agent tool, is not empty whitespace.

**With narrowing, the claim survives.** What remains genuinely unoccupied is the specific composition, and each conjunct is demonstrated by the table rather than asserted:

1. **Both artifact kinds.** No swept item that signs a capability declaration covers both MCP servers and skills. Enclawed and NVIDIA cover skills only; studiomeyer, ETDI, ToolHive, Docker, and the registry cover MCP only.
2. **Composition of the four standards through a portable format.** Every neighbor that signs mints its own trust root: Enclawed uses bespoke Ed25519, studiomeyer uses TOFU pinned Ed25519, ETDI uses OAuth issued JWTs, NVIDIA uses OpenSSF Model Signing. None emits a portable in-toto DSSE predicate that composes npm provenance, Sigstore, SLSA, and CycloneDX, and none rides the supply chain trust infrastructure that already exists.
3. **An external policy loop from publication to admission.** Every neighbor that verifies does so inside its own boundary: Enclawed's gate is its own runtime at bootstrap, studiomeyer verifies per user at first use, ETDI verifies client side at discovery. None separates attestation production (the maker's mark) from an independent policy consumer (assayward) across a publish, discover, admit pipeline.

Two honesty caveats belong on the record for the gate. First, this is an integration claim, not a greenfield claim: the primitives (signed manifest, capability vocabulary, policy gate) each exist separately in prior work, and the novelty is the composite. The narrowed sentence below is worded so that it claims exactly the composite and nothing more. Second, the narrowed claim remains falsifiable, which the EB-1A discipline requires: a single prior framework demonstrated to cover both artifact kinds, compose the four standards through a portable predicate, and feed an external admission gate would falsify it. The sweep found none.

**Recommendation: GO, with §1.2 replaced by the sentence below.** If the maintainer is unwilling to retreat from the unqualified "first," the honest alternative is NO GO, because the unqualified sentence is falsified by named, citable prior art.

### (c) Replacement sentence for §1.2

> smithmark is the first attestation framework to cover both MCP servers and skills with capability declarations issued as portable, signed attestations (in-toto DSSE) for an external policy engine to consume: it composes npm provenance, Sigstore, SLSA, and CycloneDX rather than replacing them or minting a bespoke trust root, and it closes the loop from publication (maker's mark) to admission (assayward policy).

Recommended companion text, to follow the blockquote in §1.2 in place of the current "Scanners inspect; registries curate" line, so the claim names its neighbors in the same breath it distinguishes them:

> Enclawed signs skill manifests for its own runtime; studiomeyer-io/mcp-server-attestation signs tool and spawn allowlists for MCP servers under trust on first use; ETDI binds OAuth scoped tool definitions to a client side policy check. None covers both artifact kinds, none composes the existing supply chain standards, and none separates the maker's mark from the gate that consumes it. Scanners inspect; registries curate; the near neighbors sign in silos; smithmark composes.

## 3. Positioning language

The paragraphs below are written for reuse in `proposals/` and the README. Each failure mode names the competitor and cites where its own sources say the approach stops, per the standard: novelty demonstrated, never asserted.

**Scanners inspect one install at a time and produce no portable evidence.** Snyk Agent Scan (formerly Invariant Labs mcp-scan) discovers and scans agent components on a single machine for prompt injections, tool poisoning, and malware, and it does this well; but a scan is a point in time inspection, its JSON output is a findings report rather than a signed declaration, and its own documentation warns that the CLI output is experimental and not for production workflow dependence (`notes/invariant-mcp-scan.md`). Nothing a scanner emits travels with the artifact, so every consumer must rescan from scratch. An attestation is the opposite artifact: signed once by the maker, verifiable anywhere, durable across installs.

**Curation centralizes trust in the curator without binding a capability declaration to the artifact.** The MCP Registry verifies namespace ownership through GitHub, DNS, or HTTP challenge and moderates listings, but it signs nothing: the only integrity metadata in server.json today is a `fileSha256` hash, and there is no attestation reference field (`notes/mcp-registry.md`). Docker MCP Catalog and NVIDIA Verified Agent Skills go further and sign what they host: Docker "builds and signs all local servers in the catalog" with provenance and SBOM metadata, and NVIDIA's OpenSSF Model Signing signature "covers every file and subdirectory in the skill directory" (`notes/docker-mcp-catalog.md`, `notes/nvidia-verified-agent-skills.md`). Both are integrity and origin signatures by the catalog operator over the catalog's own inventory: trust concentrates in the curator, the signature says nothing about what the artifact is permitted to do, and neither emits a capability attestation that an external policy engine consumes. NVIDIA's skill cards document capabilities descriptively, for humans; they are not machine consumable, signed policy evidence.

**Provenance proves build origin, never capability.** npm provenance, where present, is exactly what it claims: a Sigstore backed SLSA predicate naming the source repository, commit, build workflow, and artifact digest. It never states what the package can do at runtime, and coverage is partial: 6 of 10 popular MCP server packages sampled on 2026-07-16 ship provenance, with the official `@modelcontextprotocol` servers present and several popular third party servers absent (`notes/npm-provenance-mcp.md`). Stacklok ToolHive consumes this layer competently, verifying Sigstore signatures and build provenance at deploy time; its own definition of verified is that a server was "built from the official GitHub repository," used "the expected GitHub Actions workflow," and was "signed by GitHub's certificate authority" (`notes/stacklok-toolhive.md`). A package with perfect provenance can still open arbitrary sockets and read arbitrary files. smithmark composes this layer rather than duplicating it and adds the layer it cannot express: the capability declaration.

**The near neighbors sign capability declarations, but in silos.** SkillGuard requires each skill to declare its capability surface in a JSON manifest and even anticipates that "skill manifests could become an expected artifact," but the manifest is unsigned and runtime enforced only; the paper does not discuss signing or attestation at all (`notes/skillguard.md`). Enclawed does sign, with an Ed25519 manifest and a gate that denies any capability not declared, but the signature anchors to its own trust root, the gate is its own runtime, and the coverage is skills only (`notes/enclawed-skills-verifiable-artifacts.md`). studiomeyer-io/mcp-server-attestation signs an MCP server's tool and spawn allowlist, while its README places network egress control, sandboxing, and OAuth hardening explicitly out of scope and its trust model is a per user TOFU pin (`notes/studiomeyer-mcp-server-attestation.md`). ETDI signs tool definitions whose capabilities are OAuth scopes, verified client side at discovery; its upstream contribution to the official MCP SDK was closed unmerged (`notes/etdi.md`). Each of these validates the demand for signed capability declarations, and each mints its own trust root, bundles its own gate, and covers one artifact kind. smithmark's position is not that these projects are wrong; it is that the evidence they produce cannot travel. smithmark issues one portable in-toto DSSE predicate for both MCP servers and skills, anchors it in the supply chain roots that already exist (Sigstore, npm provenance, SLSA, CycloneDX), and hands admission to an independent policy engine, so the maker signs once and any gate anywhere can verify.

## 4. Consequences and watch items

- **The §1.4 standards venue is already contested.** CycloneDX issue #895 asked in March 2026 for an Agent BOM covering "what is it authorised to do"; it was closed as duplicate and defines no taxonomy, so the specific agent capability taxonomy slot at TC54 remains open, but smithmark should assume company in that venue and move promptly (`notes/cyclonedx-agent-bom.md`).
- **The registry RFC gap is confirmed.** server.json has no attestation reference field today; `fileSha256` for MCPB bundles is the only integrity metadata. The §1.4 MCP Registry provenance RFC targets a real, verified gap (`notes/mcp-registry.md`).
- **§1.3 references should say Snyk Agent Scan.** The mcp-scan comparison in the requirements now points at a Snyk branded product (verified against the repository README on 2026-07-16), which also signals that the scanning side of this space is consolidating under large vendors.
- **Watch item: Ken Huang's "Agent Skill Trust & Signing Service" essay.** Seen during the 0.1 discovery sweep as a design essay proposing a skill signing service, judged not a shipped competitor and not fetched in full (Task 0.1 report, section 5). Directionally similar to smithmark's skills side; worth a full read before the M6 proposals ship.
- **Watch item: Enclawed's trajectory.** It is the nearest implemented neighbor. If it adds MCP server coverage or adopts a portable attestation format, the narrowed claim's first conjunct erodes; the composition and external policy loop conjuncts would remain.
